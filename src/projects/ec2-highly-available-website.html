Highly Available Website on EC2

Built: November 2026 Jump to START ↓
Business Requirement

Build a portfolio website on AWS that runs on Amazon EC2 instances in private subnets of a custom Amazon VPC, spread across two Availability Zones behind an Application Load Balancer, and that shows a view counter and a "latest news" feed kept in Amazon DynamoDB, with AWS Lambda updating the feed on a schedule, and a contact form that sends an email notification through Amazon SNS. Visitors must reach it only through the load balancer, and failed instances must be replaced automatically.

How would you host a web server so it survives losing an instance or an Availability Zone, and keep the servers off the public internet?

Source: Digital Cloud Training lab, "SAA1 Capstone Project 1: AWS Portfolio Website".

Figure 1 — Visitors reach only the Application Load Balancer, so the Amazon EC2 web servers can sit in private subnets and the Auto Scaling group can replace them. The NAT Gateway lets those private servers reach the internet outbound only, without letting the internet in. The three microservices bypass the servers: the page's JavaScript calls their Lambda Function URLs directly, so each one can change without touching the web servers.

Proof: the load balancer's DNS name returns the website over HTTP, the view counter goes up on each load, and the target group shows 2 of 2 targets healthy. A test run of the RSS function returned 200 "News updated successfully", and UpdateWebpageFunction returned the 10 newest posts from DynamoDB.

Problems I Hit and How I Fixed Them

Problem 1

The first EC2 website would not load
Trying to: open the website on the first Amazon EC2 instance I launched from the provided AMI.
What happened: the browser could not connect.
Why: the AMI already held the HTML, CSS and PNG files, so the site was fine. The instance's security group did not allow inbound HTTP on port 80, so the request never reached the web server.

Fix
  1. EC2 → Instances → select the instance → Security tab → click its security group.
  2. Edit inbound rules → Add rule: type HTTP, port 80 → Save rules, then reload the site.
Problem 2

The Latest News function had no URL
Trying to: show the news records on the website.
What happened: nothing loaded, although UpdateWebpageFunction could read the DynamoDB records.
Why: the website's JavaScript runs in the visitor's browser and needs an address to call, and the function had no Function URL. The course's CloudFormation template creates the function but not a Function URL.

Fix
  1. Lambda → Functions → UpdateWebpageFunction → Configuration → Function URL → Create function URL.
  2. Choose auth type NONE so the browser can call it, then use the URL in the website's JavaScript.
Problem 3

The Function URL returned 403
Trying to: call the new Function URL from the browser.
What happened: a 403 Forbidden response.
Why: the URL existed, but a public Function URL needs two permissions in the function's resource-based policy, lambda:InvokeFunctionUrl and lambda:InvokeFunction, and one or both were missing.

Fix
  1. Lambda → UpdateWebpageFunction → Configuration → Permissions → Resource-based policy statements.
  2. Check that statements allow both lambda:InvokeFunctionUrl and lambda:InvokeFunction for public access; add whichever is missing with Add permissions.
  3. Call the URL again.
Problem 4

The private subnets had no route to the internet
Trying to: give the instances in the private subnets outbound internet access.
What happened: the private route table existed, but its default route (0.0.0.0/0) had nowhere to point.
Why: I had not created the NAT Gateway the route needs as its target.

Fix
  1. VPC → NAT gateways → Create NAT gateway: pick a public subnet and let it allocate an Elastic IP automatically.
  2. VPC → Route tables → the private route table → Routes → Edit routes: 0.0.0.0/0 → the NAT Gateway.
Problem 5

The target group timed out
Trying to: get the instances healthy in the load balancer's target group.
What happened: the health checks timed out.
Why: on the instance's Security tab, the inbound port-80 rule showed portfolio-web-sg itself as the source. Traffic from the load balancer comes from the ALB security group, so it never matched the rule.

Fix
  1. EC2 → Security Groups → portfolio-web-sg → Inbound rules → Edit inbound rules.
  2. On the HTTP 80 rule, change Source from portfolio-web-sg to the ALB security group → Save rules.
  3. Wait for the targets to show healthy, then open the ALB's DNS name.

Lesson: in a security group rule the source says who may connect, so for a load-balanced server it must be the load balancer's group.

Design Considerations

CategoryDecisionHow I'd explain itStatus
Requirements & workloadA public website that must stay up if an instance or Availability Zone fails, plus a news feed that updates itself."The site has to keep running if one server or one zone is lost."Addressed
Scalability & performanceAn Auto Scaling group launches identical servers from one launch template behind the load balancer. I set its desired capacity to 2. Load not tested."Every server comes from the same template, I run two, and I have not load-tested it."Partly addressed
Availability & fault toleranceSubnets and the load balancer span two Availability Zones, and the Auto Scaling group launches into both private subnets with the EC2 and ELB health check types on, so it can replace an instance the load balancer marks unhealthy. There is one NAT Gateway, in one public subnet, so it is a single point for outbound traffic."Two zones and automatic replacement cover the servers, but the one NAT Gateway is still a single point."Partly addressed
Data & consistencyNews records live in DynamoDB, not on the servers, so replacing an instance loses nothing. A daily EventBridge schedule runs the RSS function, which writes the 10 newest posts to the AWSNews table, and UpdateWebpageFunction reads them."The servers hold no data, so replacing one loses nothing."Addressed
SecurityInstances are in private subnets. portfolio-web-sg accepts HTTP only from the ALB security group, not from the internet (Problem 5). The Function URLs use auth type NONE, so anyone can call them. Each Lambda function has its own IAM role, limited to its own table or SNS topic. This build is HTTP on port 80 only, with no HTTPS or custom domain; the S3 case study covers those."Only the load balancer can reach the servers and each function has its own narrow role, but the Function URLs are public and this build is HTTP only."Partly addressed
ObservabilityThe target group's health checks show whether instances are healthy. No alarms or dashboards were set up.—Not addressed yet

The VPC, load balancer and Auto Scaling group were built by hand in the AWS console, in order, testing as I went.

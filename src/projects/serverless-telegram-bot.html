Serverless Telegram Bot on AWS Lambda

Built: September 2026
Business Requirement

Build a Telegram bot that answers a small bakery's sales questions from live Square data, with no server to keep running, a public HTTPS address that only genuine Telegram messages can use, and a bill close to $0.

How would you host a chat bot that is idle most of the day?

Key decision
Amazon API Gateway HTTP API in front of an AWS Lambda container image, because Lambda's own public URL was blocked
Stack
AWS Lambda, API Gateway, Amazon Elastic Container Registry (ECR), AWS Identity and Access Management (IAM), Terraform, GitHub Actions, in us-east-1
Monthly cost
Under $1 (estimate), mostly image storage
Status
Live, auto-deploy on every merge to main

Figure 1 — Messages reach Lambda through API Gateway, which needs no request signing, so Telegram can call it. A container image carries the charting libraries that do not fit a zip package. The daily report is separate: a GitHub Actions schedule sends it to Telegram without using AWS.

Problems I Hit and How I Fixed Them

The bot first ran on my laptop by polling Telegram. Moving it to AWS broke four things.

Problem 1

Lambda's own public URL was blocked
Trying to: give Telegram an HTTPS address to post messages to. A Lambda Function URL was my first choice.
What happened: my AWS account blocks Function URLs that allow anonymous calls.
Why: Telegram cannot sign requests with AWS credentials. Putting Amazon CloudFront in front of a signed Function URL did not help either, because Lambda wants a payload hash that only an AWS-aware client can compute.

Fix
  1. In infra/apigateway.tf, define an HTTP API with a $default route and an AWS_PROXY integration to the function.
  2. Add an aws_lambda_permission so API Gateway may invoke the function.
  3. Because the address has no AWS-level login, the handler checks the X-Telegram-Bot-Api-Secret-Token header and returns 401 if it is missing or wrong.
Problem 2

Lambda rejected my Docker image
Trying to: create and update the function from an image built on my laptop.
What happened: Lambda refused it with image manifest ... is not supported.
Why: current Docker Desktop attaches extra provenance and SBOM (software bill of materials) manifests, and Lambda does not accept an image built that way.

Fix
  1. Build with docker build --provenance=false --sbom=false.
  2. Add the same flags to the build step in .github/workflows/deploy-bot.yml.
Problem 3

The Python 3.11 base image would not build
Trying to: install numpy and matplotlib into the Lambda image.
What happened: pip fell back to compiling from source, and that failed.
Why: AWS's 3.11 Lambda image sits on Amazon Linux 2, whose C library is too old for the current prebuilt wheels, and the compiler there is too old to build them.

Fix
  1. In the Dockerfile, change FROM to public.ecr.aws/lambda/python:3.12, which uses Amazon Linux 2023.
  2. In pyproject.toml, allow both 3.11 and 3.12 so one lockfile covers local work and the image.
Problem 4

Some first messages after a quiet spell were very slow
Trying to: reply with sales charts quickly.
What happened: the CloudWatch logs showed cold starts (a new Lambda container starting up) taking 2 to 10 seconds or more, and one hit Lambda's roughly 10-second start-up limit and failed.
Why: matplotlib scans about 200 font files on its first import, and Lambda wipes /tmp between containers, so the scan ran every time. Baking the cache into the image did not work, because matplotlib needs a writable folder and the image is read-only at runtime.

Fix
  1. In the Dockerfile, import matplotlib once at build time with MPLCONFIGDIR set to a seed folder, and ship that folder inside the image.
  2. Before matplotlib is imported, chart_renderer.py copies the seed folder into /tmp, so the scan becomes a small file copy.

Design Considerations

CategoryDecisionStatus
Requirements & workloadA private bot for the bakery's owners: only chat IDs on an allow-list get answers. Idle most of the day, so it runs only when a message arrives.Addressed
Scalability & performanceLambda starts one invocation per message. The handler builds fresh clients every time, trading a little speed for avoiding a reused event loop. API Gateway cuts integrations off at about 29 seconds, so day-by-day questions are capped at 180 days and monthly ones at 36 months.Addressed
Availability & fault toleranceManaged services only, with no extra redundancy built. Handled errors still return 200, because any other reply makes Telegram resend the same message. Alarms and a dead-letter queue are missing.Partly addressed
Data & consistencyn/a — no database; Square stores the sales data and the bot reads it live.n/a
SecuritySecret-token check, chat allow-list, and an execution role that can only write logs. The deploy user can reach one ECR repository and one function. Weak spots: API keys sit in Lambda environment variables, readable by anyone with console access, and the deploy user has a long-lived access key, unlike the OIDC role in my S3 pipeline.Partly addressed
ObservabilityLogs go to CloudWatch, including rejected calls and failed updates, and they found the cold-start problem. No metrics dashboard or alerts.Partly addressed
Deployment & DevOpsTerraform builds the infrastructure. A merge touching src/ runs lint and tests, pushes a commit-tagged image, updates the function and waits until it is ready. An ECR lifecycle policy keeps the latest 10 images. Terraform state is a local file, not shared.Partly addressed
Cost & trade-offsUnder $1 a month (estimate). Lambda and API Gateway bill per request, so an idle bot costs almost nothing. ECR storage is the one steady charge; the lifecycle policy stops old images piling up.

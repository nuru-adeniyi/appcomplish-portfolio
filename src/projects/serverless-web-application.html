Business Requirement

Build a serverless web application on AWS where a static web form hosted in Amazon S3 sends product-purchase details through Amazon API Gateway and AWS Lambda into an Amazon SQS queue, and a second Lambda function writes each one to an Amazon DynamoDB table. It must need no servers to manage and keep the web form, queue and database as separate pieces.

How would you accept form submissions from a website without running a server?

Key decision
An Amazon SQS queue between two Lambda functions, so receiving the form and writing to the database are separate steps
Stack
Amazon S3, Amazon API Gateway, AWS Lambda (Python 3.12), Amazon SQS, Amazon DynamoDB, AWS IAM, in us-east-1
Monthly cost
Under $1 (estimate)
Status
Built and tested in the AWS console

Figure 1 — The browser loads the form from the Amazon S3 website, which calls Amazon API Gateway. The first AWS Lambda function puts each purchase in an Amazon SQS queue, and a second function, started by the queue, writes it to Amazon DynamoDB. The queue sits between them so the two steps stay separate.

Proof: submitting the form added the item to the ProductPurchases table. The five sample message files, sent from AWS CloudShell with aws sqs send-message, all appeared in the table with no manual step between the queue and the table.

Problems I Hit and How I Fixed Them

Problem 1

The form's request was blocked with a CORS error
Trying to: submit the web form on the S3 website so the browser sends a PUT request to /productpurchase on the API.
What happened: the browser blocked the request with a 403 Forbidden and No 'Access-Control-Allow-Origin' header is present on the requested resource. I spent a while checking the Lambda function's policies and code, enabling CORS, checking the OPTIONS mock integration headers, returning Access-Control-Allow-* headers from the function and redeploying the dev stage. None of it helped, and the AI assistants I asked kept sending me back to API Gateway policies, headers and other settings.
Why: I had created the PUT method on the root resource (/) instead of under /productpurchase, so the target path had only OPTIONS. The request was not finding the right route at all, so the policies, headers and code I kept checking were never the cause.

Fix
  1. API Gateway → APIs → productPurchase → Resources → select the PUT under / → Delete method.
  2. Select /productpurchase → Create method → PUT → integration type Lambda function → turn on Lambda proxy integration → pick productPurchasesSendDataToQueue → Create method.
  3. With /productpurchase selected, check that CORS is enabled. If it is not, choose Enable CORS and save.
  4. Deploy API → stage dev, then submit the form again.

Lesson: a CORS or 403 error can mean the request is not finding a route at all. Before checking policies, headers or code, confirm the PUT method is nested under /productpurchase and not left at the root /.
